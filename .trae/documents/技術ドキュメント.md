# TOEIC重要単語（toeic_website_ver2.0）技術ドキュメント

最終更新日: 2026-09-02（お気に入り復習・聞き流しのログイン後の着地をマイページに統一）

## 1. プロジェクト概要

### 1.1 目的と背景

* TOEIC頻出の重要単語を、一覧・検索・詳細表示（AI生成の解説）で効率良く学習できるWebアプリを提供する

* 単語の詳細解説は、外部AI（Google Gemini）で生成し、再利用可能なキャッシュ（Upstash Redis）でコストと待ち時間を削減する

* 発音確認のため、外部TTS（Google Cloud Text-to-Speech）で音声を生成する

* 単語学習モード（ランダム出題）で、学習のリズムを作る

### 1.3 システムアーキテクチャ概要図

```
ユーザー（ブラウザ）
  └─ 表示・操作
       └─ Next.js（App Router）
            ├─ ページ
            │    ├─ /        （トップ・一覧）
            │    ├─ /study   （学習モード）
            │    ├─ /favorites （お気に入り）
            │    ├─ /favorites/listen（お気に入り単語 聞き流しモード／ログイン必須）
            │    ├─ /review    （復習モード／ログイン必須）
            │    ├─ /today-words（今日おすすめ6単語）
            │    ├─ /today-words/listen（今日おすすめ6単語 聞き流しモード／Beta）
            │    ├─ /words   （全単語一覧インデックス）
            │    ├─ /words/[word]（単語詳細）
            │    ├─ /about, /privacy, /terms, /contact, /donate （静的ページ）
            │    └─ /guide, /guide/[slug] （学習ガイド一覧／個別記事 ─ SSG）
            │
            ├─ サーバ側データ取得（Server Component）
            │    └─ src/data/word-detail.ts:getWordDetail
            │         ├─ L1: Next.js Data Cache（"use cache" + cacheLife("max") + cacheTag(`word-detail-${slug}`, "word-detail")）
            │         ├─ L2: Upstash Redis（src/lib/wordCache.ts）
            │         └─ L3: Google Gemini で詳細JSON生成→正規化→Redis保存
            │    （Server Action `fetchWordDetail` は `src/actions/word.ts` に定義された `getWordDetail` の薄いラッパー）
            │
            ├─ 単語リスト取得（src/data/words.ts）
            │    └─ Vercel Blobから取得（Next.js Data Cache: cacheTag("word-list") + cacheLife("max")）
            │
            ├─ Proxy（src/proxy.ts）
            │    └─ 拡張子なしページルートのみを対象に、Server Actions以外のPOSTを405で遮断
            │       （現在はVercel Middlewareの利用量を削減するため、matcherを空にして無効化中）
            │
            └─ API（Route Handlers）
                 ├─ POST /api/tts
                 │    └─ Google Cloud Text-to-Speech を呼び出し、Base64音声(MP3)を返却
                 ├─ GET /api/revalidate/words
                 │    └─ Next.js Data Cache（word-list）を無効化し、最新の単語リストを再取得させる
                 ├─ GET /api/revalidate/word
                 │    └─ L1（Next.js Data Cache `word-detail-${slug}`）の特定単語キャッシュをクリア。upstash=trueパラメータでL2（Redis）もクリア可能。
                 ├─ GET /api/revalidate/upstash-word
                 │    └─ Upstash Redis（L2）の `word:<slug>` キーを削除（L1は触らない）
                 └─ GET /api/sitemap
                      └─ サイトマップ(XML)を動的生成して返却（`/sitemap.xml` から rewrite）。
```

### 2.2 動作環境条件

#### 必須の環境変数

`.env.example` に定義された以下を設定する（開発は `.env.local` を推奨）。

* `GEMINI_API_KEY`: Gemini APIキー

* `TTS_API_KEY`: Google Cloud Text-to-Speech APIキー

* `UPSTASH_REDIS_REST_URL`: Upstash Redis REST URL

* `UPSTASH_REDIS_REST_TOKEN`: Upstash Redis REST Token

* `UPSTASH_VECTOR_REST_URL`: Upstash Vector REST URL（セマンティック検索。インデックスは768次元・cosineで作成すること）

* `UPSTASH_VECTOR_REST_TOKEN`: Upstash Vector REST Token（セマンティック検索）

* `SEMANTIC_SEARCH_MIN_SCORE`: セマンティック検索で返す最低類似度（任意、既定値 `0.82`、範囲 `0`〜`1`）

* `WORD_CACHE_TTL_DAYS`: 単語詳細キャッシュTTL（日）。未設定時は30日

* `BLOB_READ_WRITE_TOKEN`: Vercel Blob（単語リストファイル取得）用のトークン

* `BLOB_URL_IMPORTANT`: 重要単語ファイルの直接URL（設定時、Vercelのlist操作をスキップ）

* `BLOB_URL_MEDIUM`: 中重要単語ファイルの直接URL（設定時、Vercelのlist操作をスキップ）

* `BLOB_URL_HIGH`: 高難易度単語ファイルの直接URL（設定時、Vercelのlist操作をスキップ）

* `REVALIDATION_TOKEN`: キャッシュ再検証API保護用のトークン（推測困難なランダム文字列推奨）

* `NEXT_PUBLIC_GA_ID`: Google Analytics 4 測定ID（G-XXXXXXXXXX）

* `NEXT_PUBLIC_ADSENSE_REVIEW`: （任意）`1` または `true` で AdSense 審査モードを有効化。単語詳細ページ（`/words/[word]`）への `robots: noindex` 付与・`sitemap.xml` からの単語URL除外・A8アフィリエイトバナー非表示・TOP／学習ガイドに限定したAdSenseスクリプトの停止をまとめて切り替える（判定は `src/lib/adsense-review.ts` の `isAdsenseReviewMode()` に集約）。値はビルド時にインライン化されるため、変更にはVercelでの再デプロイが必要。審査承認後はこの変数を削除（または `0`）にして再デプロイすれば単語ページのindexと対象ページの広告読み込みが戻る

* `NEXT_PUBLIC_SUPABASE_URL`: Supabase プロジェクト URL（任意ログイン + お気に入り同期）

* `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: Supabase Publishable キー（クライアント公開前提。データアクセスは RLS で保護）

#### 開発支援MCP用の環境変数（任意）

リポジトリ直下の `.mcp.json` をClaude Codeで利用する場合は、Claude Codeを起動する親シェルに以下を設定する。アプリ用の `.env.local` は親シェルへ自動exportされないため、MCP認証情報はシェル環境または安全なシークレット管理手段から渡す。

* `GITHUB_MCP_PAT`: GitHub MCPの認証用Personal Access Token。必要最小限のリポジトリ権限を付与する

* `UPSTASH_EMAIL`: Upstashアカウントのメールアドレス

* `UPSTASH_API_KEY`: UpstashアカウントAPIキー。リソース変更が不要な場合は読み取り専用キーを使用する

認証情報の実値は `.mcp.json` やその他のGit管理対象ファイルへ保存しない。

#### データ要件

* 単語一覧は Vercel Blob 上の `words-file/word.txt`（最重要単語: 600点レベル）、`words-file/word_mid.txt`（中級単語: 730〜800点レベル）、`words-file/word_high.txt`（高難易度単語: 800点以上レベル）の3ファイルをソースとして読み込む

  * 実装は `src/data/words.ts` でデータ取得を行う（`NODE_ENV=development` 時はローカルの `__words__/` 配下を読む）。ローカル／Blob の分岐と取得処理そのものは `src/lib/word-source.ts`（`server-only` なし）に集約し、`src/data/words.ts` はキャッシュ層（`'use cache'` / `cacheTag('word-list')`）としてこれを呼び出す。CLI の `scripts/embed-words.ts` も同じモジュールを使うため、サイトと投入対象のコーパスが一致する

  * 環境変数 `BLOB_URL_IMPORTANT`, `BLOB_URL_MEDIUM`, `BLOB_URL_HIGH` の3つがすべて設定されている場合は、`list` 操作を行わず指定URLから直接取得する（高速化・API節約）

  * 上記環境変数が未設定の場合は、`@vercel/blob` の `list` を用いてBlobから単語ファイルを取得する（`BLOB_READ_WRITE_TOKEN` が必要）

  * 取得結果は Next.js の `"use cache"` 指示により `cacheTag('word-list')` / `cacheLife('max')` 付きでキャッシュされる

  * Blob 取得の失敗（非 200 応答・fetch 例外・対象 Blob の欠損）は空配列で握りつぶさず例外を投げる。例外時はキャッシュに書き込まれず、バックグラウンド再検証の失敗時は直前の正常なキャッシュが使われ続けるため、「空の単語リストが長期キャッシュされて単語が消える」事故を防ぐ（ビルド時に Blob 取得が失敗した場合はビルド自体が失敗する）

  * `slug` は `term.toLowerCase()` で生成し、最重要/中級/高難易度を統合する際に同一slugは重複排除される（各単語は `level: 'important' | 'medium' | 'high'` を保持）

#### データ更新フロー

1. Vercel Blob 上の単語ファイルを更新・アップロードする
2. `GET /api/revalidate/words?token=...` を呼び出す
3. Next.js Data Cache が Stale（期限切れ）となり、次回のアクセスで最新データが再取得される

   * 環境変数 `BLOB_URL_*` 設定時: 直接URLへアクセス（list操作なし）

   * 環境変数未設定時: Blobの `list` 操作を行い、新しいURLを取得してアクセス

### 2.4 パフォーマンス指標

外部API（Gemini/TTS）の応答時間に強く依存するため、本項は「観測可能な指標」と「目標」を定義する。

#### 観測可能な指標

* キャッシュ階層

  * L1: Next.js Data Cache（`src/actions/word.ts` の `getWordDetail` が `cacheLife("max")` を指定）

  * L2: Upstash Redis（`src/lib/wordCache.ts` が `WORD_CACHE_TTL_DAYS` をTTLとして設定）

* 生成時の挙動

  * Redisが利用できない場合でも Gemini 生成は継続し、生成結果はRedisへ保存できない（ログに警告が出る）

#### 目標（運用基準）

* L1/L2キャッシュヒット時は体感的に即時（待ちを最小化）

* 生成（Gemini）に失敗した場合も、ユーザーが一覧へ戻れるUIを提供する

## 3. 技術詳細

### 3.1 採用技術の選定理由

* Next.js（App Router）

  * ページ/UIとAPI（Route Handlers）を同一リポジトリで管理でき、Vercelへのデプロイが容易

  * 静的生成/サーバ実行を用途に応じて使い分け可能

* Google Gemini（@google/genai の GoogleGenAI）

  * モデル: `gemini-2.5-flash-lite` を採用し、高速かつ安価に生成
  * TOEIC向けの「所定JSONスキーマ」で語義・例文等を生成する用途に適合

* Upstash Redis

  * サーバレス環境と相性が良いRESTベースのRedisで、生成結果を長期TTLで再利用可能

* Google Cloud Text-to-Speech

  * 発音音声をMP3で生成し、ブラウザで即再生できる
  * 高品質なニューラル音声（Neural2）やWaveNet音声を使用

#### 外部API呼び出しのタイムアウトとリトライ

外部HTTP呼び出しの方針は `src/lib/http-retry.ts` に集約する。`server-only` は付けない（`scripts/embed-words.ts` からも使うため）。クライアントコンポーネントからは import しないこと。

* **すべての外部呼び出しにタイムアウトを設ける**。応答を返さない上流を掴んだままだと Vercel の Function が `maxDuration` まで枠を占有する。用途別の値は `HTTP_TIMEOUT_MS`（`tts` / `blob` / `font` / `redis` / `vector`）。Vercel Blob の `list()` だけは、SDK 2.x が `AbortSignal.timeout()` の `TimeoutError` を network error として再送し得るため、timer から reason なしの `AbortController.abort()` を呼んで `AbortError` として即時停止させる
* **素の `fetch` は `fetchWithRetry` を通す**（Google TTS、Vercel Blob の単語リスト、Google Fonts、Upstash Vector の Custom Requester）。`consume` callback で `json()` / `text()` / `arrayBuffer()` まで retry 境界内に置き、ヘッダー到着後の切断・本文タイムアウトも再送する。失敗時は `.status` を持つ `HttpResponseError` で reject するため、呼び出し側が 4xx / 5xx を区別できる
* **再送で結果が変わり得るものだけ再送する**。`isRetryableStatus` は `408/425/500/502/503/504` を許可し、**429 は意図的に除外**する（Gemini・Google Cloud TTS は従量課金で、レート超過時の再送は quota を余計に消費するだけ）。`501/505` は恒久的な非対応として除外
* **`AbortSignal.timeout()` はワンショットなので、必ず試行ごとに生成する**。リトライループの外で1度だけ作ると2回目以降が即中断され、リトライが実質無効になる。この退行を防ぐテストを `http-retry.test.ts` に置いている
* **Gemini SDK の内蔵リトライは使わない**。`@google/genai` 1.50.x は `retryOptions` が存在すると429も再送し、最終エラーを `status` のない通常の `Error` に変える（`attempts: 1` でも status は失われる）。各呼び出しを `retryWithTimeout` + `GEMINI_RETRY_POLICY` で包み、429を再送せず、試行ごとに timeout signal を作り直す。`generateWordDetail` の第2プロンプトは空／不正JSONのときだけ送り、transport/API失敗時は送らない
* **Upstash Redis と Vector は方針を分ける**。Redis は公式SDKの command 全体 timeout と network retry 1回だけを使い、曖昧な失敗後に `INCR` 等を二重実行し得る HTTP 5xx 再送は行わない。Vector は公開 Custom Requester（`src/lib/vector-requester.ts`）を使い、同じ入力の再送が安全な query / upsert / delete 等に対して対象HTTP 5xxを2回再送し、statusを保持する
* **Route Handler は `classifyUpstreamFailure` で上流障害を写像する**。SDK固有エラーの `status` / `statusCode` とネストした `cause` も構造的に読み、上流429→429、上流5xx→502、タイムアウト／abort→504、それ以外→500とする。すべて500に丸めると「上流の一時障害」「レート超過」「こちらのバグ」をクライアントもログも区別できない

### 3.2 主要なライブラリと依存関係

* `next`, `react`, `react-dom`: アプリ本体
* `tailwindcss`, `postcss`, `autoprefixer`: CSSフレームワークとビルドツール
* `@google/genai`（`GoogleGenAI`）: サーバ側データ取得（`src/data/word-detail.ts`）でGeminiを呼び出す
* `@upstash/redis`: サーバ側キャッシュ（`src/lib/upstash.ts`, `src/lib/wordCache.ts`）
* `@vercel/blob`: Vercel Blob から単語リストファイル（`words-file/word.txt`, `word_mid.txt`, `word_high.txt`）を取得する
* `@vercel/analytics`, `@vercel/speed-insights`: アクセス解析・パフォーマンス計測
* `@next/third-parties`: Google Analytics 4 (`<GoogleAnalytics>`) 組み込み用
* `lucide-react`: UI内で利用するアイコンコンポーネント
* `react-share`: SNSシェア機能の実装
* `p-retry`: 外部HTTP呼び出しとSDK処理の選択的再送（`src/lib/http-retry.ts`）。Google TTS / Vercel Blob / Google Fonts / Upstash Vector Custom Requester の `fetchWithRetry` と、内蔵retryを無効化したGeminiの `retryWithTimeout` に使用する。Redisは非冪等コマンド保護のためSDKのnetwork retryだけを使う
* `server-only`: Next.js のモジュールグラフ内で、サーバー専用コードの Client Component への誤 import を防止する。`scripts/embed-words.ts` のようにNode/`tsx` が直接実行するCLIでは、通常のNode条件でパッケージの既定エントリが例外を投げるため import しない。代わりに Client Component から参照不可とする
* `babel-plugin-react-compiler`: React Compilerによる自動メモ化（`next.config.ts` で `reactCompiler: true` を指定、`cacheComponents: true` も併用）

#### MCP開発支援（任意）


* Upstash MCPは現行CLI形式（`@upstash/mcp-server@latest --email ... --api-key ...`）で起動する。書き込み操作が不要な開発者は読み取り専用APIキーを使用する
* プロジェクトスコープのMCPサーバーは、Claude Codeの初回利用時に内容を確認して承認する

#### 共有/ユーティリティ/Hooks

* 単語データ `src/data/words.ts` / 取得元ローダー `src/lib/word-source.ts`

  * 開発時は `__words__/word.txt`, `__words__/word_mid.txt`, `__words__/word_high.txt` を読み込み、本番は Vercel Blob から取得（分岐は `word-source.ts` の `resolveDefaultWordSource()` に集約）

  * `"use cache"` + `cacheTag('word-list')` + `cacheLife('max')` でデータキャッシュ（React の `cache()` でリクエスト内メモ化）。本番の Blob 取得失敗は例外として伝播させ、空リストの長期キャッシュ化を防ぐ

  * `getAllWords` / `getImportantWords` / `getMediumWords` / `getHighWords` / `getWordBySlug` / `getTodayRecommendedSelection` / `getTodayRecommendedWords` を提供
  * `getTodayRecommendedSelection(limit)` は `'use cache'` + `cacheTag('today-recommended-words', 'word-list')` + `cacheLife('max')` を付与した Cache Component。`limit` の既定値は `TODAY_WORDS_COUNT`。選定6語 `words`、日付キー `dateKey`、slug集合から作る8桁の `wordListVersion` を返す。`word-list` タグも持つため単語リスト更新時に派生選定も stale になる。JST 7:05 の Vercel Cron が `revalidateTag('today-recommended-words', 'max')` を実行するため、時間ベースの日次再検証は併用しない
  * `getTodayRecommendedWords(limit)` は `getTodayRecommendedSelection` を包んで `words` だけを返す**キャッシュなし**のラッパー。`'use cache'` を二重に置くとキャッシュエントリが2つになるため、キャッシュ境界は `getTodayRecommendedSelection` 側だけに持たせる
  * **運用上の前提**: `cacheLife('max')` は自己失効しないため、日次回転は Cron（`/api/revalidate/today-words`）の発火に完全依存する。Cron が停止・遅延すると同じ6語が無期限に固定されるため、Cron の死活監視／アラートを前提とする。`'days'` 等の時間ベース失効を併用すると Cron と二重に stale 化し書き込みが増えるため、バックストップとしては採用しない

  * `getRelatedWords` は `connection()` を使用して動的レンダリングを行い、`Math.random()` によりリクエスト毎に同レベルのランダムな関連単語を取得する機能を提供

* Favorites Context `src/context/FavoritesContext.tsx`

  * `localStorage`（未ログイン）と Supabase（ログイン中）をバックエンドとしたお気に入り単語の状態管理
  * `localStorage` は `src/lib/favorites-store.ts` の外部ストアとして `useSyncExternalStore` で購読する。マウント時に effect から `setState` する必要がなくなり、`react-hooks/set-state-in-effect` に抵触しない。SSR・ハイドレーション時は `getServerSnapshot()` が空配列を返すため描画の食い違いも起きない
  * `AuthContext` はユーザーIDが切り替わるたびに `authEpoch` を増やす。Supabase由来のremoteには `userId` と `authEpoch` の両方を記録し、現在の認証世代と一致する取得済みremoteだけを正とする。同一アカウントへの再ログインでも古いremoteを使わないため、Supabase再取得が失敗してもログアウト中に追加したlocalStorageのお気に入りを隠したり上書きしたりしない
  * ログアウト時の `localStorage` 書き戻しは layout effect で行う。`useEffect` だと書き戻し前の1フレームが描画され、D-2 で修正した「ログアウトでお気に入りが消えたように見える」症状が再発するため。書き戻し対象は直前の `authEpoch` で取得済みのremoteだけに限定する
  * `favoritesStatus`（`guest` / `loading` / `ready` / `error`）と `retryFavoritesSync()` を公開する。ログイン必須の画面（マイページ・復習キュー）は `ready` のときだけ描画することで、Supabase 取得前の `localStorage` の値を表示しない。復習画面で `error` の場合はローカル値へフォールバックせず再試行させる

* Favorites Store `src/lib/favorites-store.ts`

  * `localStorage` を `useSyncExternalStore` から購読するための外部ストア（`subscribe` / `getSnapshot` / `getServerSnapshot`）
  * `getSnapshot()` は生の文字列が変わったときだけパースし直してキャッシュする（毎回新しい配列を返すと再レンダリングが無限に走るため）
  * 自タブの書き込みは `emit()` で明示通知し、他タブの変更は `storage` イベントで追随する
  * ブラウザ設定などで `localStorage` の読み書きが拒否された場合は、最新スナップショットをメモリに保持するvolatile fallbackへ切り替える。永続化はできなくても現在のタブでは追加・削除・クリアを継続できる
  * 副作用を持つため、純ロジックの `favorites-sync.ts` とは分離している

* 復習スケジュール（純ロジック） `src/lib/review-schedule.ts`

  * Leitner ボックス方式の復習間隔（box 1..5 = 1 / 3 / 7 / 14 / 30日）と、期限判定・優先度付け・集計・連続日数更新・Supabase行との相互変換をまとめた副作用のないモジュール（ユニットテスト対象）

* SEO

  * トップOGP画像 `src/app/opengraph-image.tsx`（Edge Runtime）
  * 単語別OGP画像 `src/app/words/[word]/opengraph-image.tsx`（各単語のタイトル＋日本語訳を描画）
  * **OGP画像のActive CPU対策**：`cacheComponents: true` の環境では metadata image route（`opengraph-image`）がビルド時にプリレンダリングされず、`generateStaticParams` / `dynamicParams = false` を付けても動的（ƒ）のままになる。そのため単語別OGPルートは両者を**持たない**。付けても出力は1枚も生まれない一方で、ビルドの静的生成対象だけが単語数ぶん増える（1,422 → 2,798ページ）ため、ローカルビルドが実測で静的生成 9.1s → 28.2s、全体 17s → 35s、macOSの圧縮メモリ 4.7GB → 11.4GB、swapin 1.4万 → 20万回まで悪化していた。未知スラッグの排除は Function 内の `getWordBySlug` チェックで代替し、画像を描かず `OG_IMAGE_NOT_FOUND_CACHE_CONTROL`（`s-maxage=3600`）付きの404を返す。データアクセスを一切持たない最小構成でも ƒ になること、`prerender-manifest.json` 上のOGPルートが0件であることを実測で確認済み。`export const revalidate` も同環境では無効。OGP画像1枚の生成は Satori のレイアウト計算と resvg による 1200x630 PNG のラスタライズを伴い Active CPU を大きく消費するため、放置するとリクエスト数に比例してCPUを焼く（Vercel Fluid の Active CPU 逼迫の主因）。対策として `OG_IMAGE_CACHE_CONTROL`（`src/lib/og-utils.ts`）を両OGPルートのレスポンスヘッダに付与し、CDN側で保持してFunction実行を「エッジごとに一度」まで畳む。`s-maxage` は単語詳細キャッシュ（`WORD_CACHE_TTL_DAYS` 既定30日／`cacheLife("max")`）と歩調を合わせた30日、期限切れ後も `stale-while-revalidate` で配信を止めない。あわせて `loadGoogleFont` を `'use cache'`（`cacheTag('og-font')` + `cacheLife('max')`）にし、画像生成ごとに発生していた Google Fonts への往復2回を除去した
  * **OGPフォントキャッシュのOOM対策**：`loadGoogleFont` は Google Fonts の `text=` を付けない安定したフルTTF URLを両OGPで共有する。サーバー向け truetype は `text=` が違っても実体が同じ約7MBのフォントだが、URL／キャッシュキーは文字列ごとに変わる。単語数分を保持した実測キャッシュは約10GBまで膨張しVercelの8GBビルドでOOMになったため、安定URL化してフォントキャッシュを1エントリへ集約する
  * robots `src/app/robots.ts` / sitemap `src/app/api/sitemap/route.ts`（動的生成、`/sitemap.xml` へrewrite）。robots は App Router のメタデータルート `robots.ts` が唯一の生成元（旧 `public/robots.txt` は競合する残骸だったため削除済み）。sitemap には `noindex` ページ（`/favorites`・`/review`・`/login`・`*/listen`）を掲載しない（sitemap 掲載と `noindex` は矛盾シグナルになるため）。`lastmod` は静的ページ・ガイド記事のみ出力し、実更新日を管理していない URL（全単語詳細ページ、および日次ローテーションする `/today-words`）では出力しない（同一固定日を出すと Google が lastmod を信用しなくなるため、偽の日付を出すより省略する方針。`changefreq`/`priority` は残置しているが Google は無視する）
  * 学習ガイドは `indexable !== false` の記事だけを一覧・`generateStaticParams`・関連記事・sitemapへ出す。保留記事の直接URLは `noindex, nofollow` とし、内容確認が完了するまで公開記事数に含めない
  * manifest `src/app/manifest.ts` (PWA対応)
  * JSON-LD 生成ヘルパ `src/lib/json-ld.ts`（単語詳細用 Article/DefinedTerm など）
  * **【調査中】Googlebot への切断 HTML 問題**: 本番の UA 別テストで、キャッシュ未生成（Vercel `x-vercel-cache: BYPASS`）の単語ページにおいて**メインクローラー Googlebot だけが `<Suspense>` 未解決の切断 HTML（h1・単語解説・`DefinedTerm` JSON-LD なし、`</html>` 欠落）を受信**する現象を確認（Bingbot/Slackbot は同 BYPASS でも完全 HTML）。当初 `next.config.ts` の `htmlLimitedBots` 上書きで対処を試みたが、Next.js ソース精査（`is-bot.js`／`streaming-metadata.js`／`app-page.js:349,372`）の結果、(1) `htmlLimitedBots` はメタデータのストリーミング可否 (`shouldServeStreamingMetadata`) にしか影響せず本体バッファには無関係、(2) `Googlebot` の botType はハードコードの `HEADLESS_BROWSER_BOT_UA_RE` で `'dom'` 判定され設定では不変、(3) `shouldWaitOnAllReady = Boolean(botType) && isRoutePPREnabled` は Googlebot/Bingbot 双方で既に true——であることが判明。よって設定変更は本問題に無効と結論しリバート。オープンソースのコード上は両 bot とも完全 HTML になるはずのため、原因は Vercel/ビルド層にあると推定し**ローカル再現（`npm run build && npm run start` + Googlebot UA）で Next.js 起因か Vercel 起因かを切り分けるのが次の一手**。有力な恒久対策候補は `words/[word]/page.tsx` の `next/dynamic`＋`<Suspense>` の動的境界を撤去し `getWordDetail`（`"use cache"`）を直接 await して単語本体を静的プリレンダーに含めること。詳細な調査記録・検証手順は `__docs__/seo-audit-action-plan.md`

### 4.2 コンポーネント間の連携フロー

#### 単語詳細の取得（AI + 多段キャッシュ）

1. ブラウザが `/words/[word]` を開く
2. Server Component（`src/app/words/[word]/page.tsx`）が `getWordDetail(word)` を呼ぶ
3. `getWordDetail` は次の順に取得する

   * L1: Next.js Data Cache（ヒットすれば即返却）

   * L2: Upstash Redis（ヒットすれば即返却）

   * L3: Geminiで生成 → 正規化 → Redisへ保存 → 返却
4. クライアントはSSRされた `initialData` を描画する（`WordDetailClient`）

#### 今日おすすめ6語の選出

1. Server Component（TOP `/`、`/today-words`）が `getTodayRecommendedSelection()` を、`/today-words/listen` が薄いラッパー `getTodayRecommendedWords()` を呼び出す
2. `getTodayRecommendedSelection` は `'use cache'` Cache Component。UTC日付キー + `slug` の FNV-1a ハッシュで安定ソートし、先頭6語を日付キー・コーパス版と一緒に返却する。キャッシュは `cacheLife('max')` で長期保持し、毎日 JST 7:05 の Cronまたは `word-list` タグで再検証する
3. `TodayRecommendedWordsClient` は詳細リンクへ `from=today&today=<日付キー>&v=<8桁版>` を付与する（6語のslug列は載せない）
4. 単語詳細の `WordNavigation` は日次キャッシュを取得せず、`WordNavigationClient` が純粋関数 `resolveTodayNavigationSelection()` で日付・版・現在語の所属を検証して6語を再計算する。コーパス更新、欠落、不正、旧形式では全単語ナビにフォールバックする
5. `TodayWordsListenClient` は選定済みの6語を props で受け取るのみで、選定ロジックを持たない（単一ソース化）
6. 同一日内は同一セットになり、日付が変わるとセットが切り替わる

#### 聞き流しモードの再生フロー

1. ユーザーが「今日おすすめの6単語」エリアの「聞き流し(Beta)」ボタンから `/today-words/listen` に遷移
2. Server Component が `getTodayRecommendedWords()` で6語を取得し、`TodayWordsListenClient` に渡す
3. クライアントは現在語＋次の語の `WordDetails` を `fetchWordDetail`（Server Action）経由で prefetch（例文の即時表示用）
4. 再生ボタンで「単語 → 英語例文 → 日本語例文」の順に `fetchTTS` を呼び、Audio 要素で順次再生
5. 各遷移は `audio.onended` で発火し、ref 経由で「自分が現役か」を検査してから次のステップへ進む
6. 最終単語の最終ステップ完了で完了メッセージを表示し、再生ボタンで先頭から再開可能

#### 発音音声の生成（TTS）

1. クライアント（`useTTS`）が `POST /api/tts` に `{ "text": "word", "language": "en" }` を送信
2. サーバが `TTS_API_KEY` を `x-goog-api-key` リクエストヘッダーで送信して Google Text-to-Speech API を呼び出し、`audioContent`（Base64）を取得。APIキーはURLに含めず、ブラウザにも返却しない
3. ブラウザが `data:audio/mp3;base64,...` として生成し、再生する

### 4.3 API仕様

#### 4.3.1 `POST /api/tts`

* 概要: 指定テキストの英語または日本語音声（MP3）を生成して返す

* ヘッダー:
  * `Content-Type: application/json`
  * `X-App-Source: toeic-client` （必須）

* リクエストボディ（JSON）

  * `text`: string（必須, 最大500文字）
  * `language`: "en" | "ja"（任意, デフォルト "en"）
  * `wordSlug`: string（任意。例文 TTS の場合は必須）

* セキュリティガード（順に評価）

  1. `X-App-Source: toeic-client` ヘッダーが必須
  2. `Origin` または `Referer` が `host` を含むこと
  3. `text.length <= 500`
  4. **Allowlist 検証**:
     * 単一英単語（空白を含まない英文）: `getWordBySlug(text.toLowerCase())` で語彙リストに存在することを確認
     * 例文（複数語、または日本語テキスト）: `wordSlug` を必須とし、Upstash Redis にキャッシュ済みの `WordDetails` を読み出して、`toeicExamples[].english/japanese` あるいは `meanings[].detailedMeanings[].example/exampleJapanese` のいずれかと完全一致（空白正規化後）すること。これにより、Referer 偽装攻撃に対する任意テキスト合成（コスト乗っ取り）を防止
  5. **レート制限**: Upstash Ratelimit による IP 単位 30 req/分（slidingWindow）。Redis にキャッシュ済みの結果を返す経路はカウンタを消費しない（cache miss のみ計上）
  6. **Google APIキー保護**: `TTS_API_KEY` は `x-goog-api-key` ヘッダーでGoogleへ送信し、URLクエリ・HTTPレスポンスには含めない

* キャッシュ階層

  * Redis 上の TTS キャッシュ（30日 TTL）。単一英単語は `tts:en:word:<slug>` キー、それ以外は `tts:<lang>:<wordSlugTag>:<sha256_12>` キー

* レスポンス（200）

  * `{ "audioContent": "<base64>" }`
  * `Cache-Control: public, max-age=86400`

* エラー

  * 400: `{ "error": "Invalid request body" }`
  * 400: `{ "error": "Text too long" }`
  * 400: `{ "error": "Word not allowed" }` — 単一英単語 allowlist に該当なし
  * 400: `{ "error": "wordSlug is required for example text" }` — 複数語または日本語テキストで `wordSlug` 未指定
  * 400: `{ "error": "Example text not allowed" }` — 例文テキストが語彙詳細の例文と一致しない
  * 403: `{ "error": "Unauthorized source" }` / `{ "error": "Unauthorized origin" }`
  * 429: `{ "error": "Too Many Requests" }` — レート制限超過。`Retry-After` / `X-RateLimit-*` ヘッダー付き
  * 500: `{ "error": "TTS_API_KEY is not configured" }` 等

#### 4.3.2 `GET /api/tts`

* 概要: 誤ったメソッド呼び出しに対するガード用エンドポイント

* レスポンス（405）

  * `{ "error": "Method Not Allowed", "message": "This endpoint requires a POST request with a JSON body containing the 'text' to synthesize." }`

#### 4.3.3 キャッシュ再検証 `GET /api/revalidate/words`

* 概要: 単語リストデータのNext.js Data Cache（`word-list`タグ）を無効化し、最新化を要求する

* クエリパラメータ

  * `token`: string（必須） - 環境変数 `REVALIDATION_TOKEN` と一致する値

* 動作

  * `revalidateTag('word-list', 'max')` を実行する

  * これにより、Data CacheはStale状態となり、次回アクセス時にバックグラウンドで最新データ（Blob）が再取得される（Stale-while-revalidate）

  * CDNキャッシュではなく、Next.jsサーバー内のData Cacheが対象

* レスポンス（200）

  * `{ "revalidated": true, "now": 1234567890 }`

* エラー

  * 401: `{ "message": "Invalid token" }`

#### 4.3.4 単語詳細キャッシュクリア `GET /api/revalidate/word`

* 概要: 特定の単語に対する L1 キャッシュ（Next.js Data Cache）をクリアする。オプションで L2 キャッシュ（Upstash Redis）もクリア可能。

* クエリパラメータ

  * `token`: string（必須） - 環境変数 `REVALIDATION_TOKEN` と一致する値
  * `slug`: string（必須） - キャッシュをクリアしたい単語（例: `additional`）
  * `upstash`: string（任意） - `true` を指定すると Upstash Redis のキャッシュも削除する
  * `vector`: string（任意） - `true` を指定すると、キャッシュクリア後に `getWordDetailFresh` で最新の WordDetails を取得し直し、embedding を再生成して Upstash Vector に upsert する（セマンティック検索の内容ズレ防止）。`upstash=true` と併用すると Gemini で完全再生成された内容が embedding に反映される

* 動作

  * `revalidateTag(\`word-detail-\${slug}\`, 'max')` を実行し、該当単語の L1 キャッシュをパージ
  * `upstash=true` の場合、`deleteWordDetails(slug)` により Redis からデータを削除
  * `vector=true` かつ Upstash Vector が設定済みの場合、`upsertWordEmbedding` により該当単語のベクトルを再投入し、成功後に Redis の `semsearch:index-version` を増分する。これにより旧世代の検索結果キャッシュは即時参照されなくなる

* レスポンス（200）

  * `{ "revalidated": true, "slug": "additional", "vectorUpdated": true, "semanticIndexVersion": 4, "message": "Cache for word 'additional' has been cleared." }`
  * Vectorを更新しなかった場合、`vectorUpdated` は `false`、`semanticIndexVersion` は `null`

* エラー

  * 400: `{ "message": "Missing slug parameter" }`
  * 401: `{ "message": "Invalid token" }`
  * 500: `{ "message": "Failed to revalidate word", "error": "..." }`

#### 4.3.4.1 Upstash（L2）単語キー削除 `GET /api/revalidate/upstash-word`

* 概要: Upstash Redis（L2）に保存された単語詳細キャッシュ（`word:<slug>`）を削除する（Next.js Data Cache（L1）は触らない）

* クエリパラメータ

  * `token`: string（必須） - 環境変数 `REVALIDATION_TOKEN` と一致する値
  * `key`: string（必須） - `word:` で始まるRedisキー（例: `word:ability`）

* 動作

  * `key` から `slug` を抽出し、`deleteWordDetails(slug)` を実行して削除する（正規化後のキーは `wordCache.ts:cacheKeyForWord` と同一）

* レスポンス（200）

  * `{ "deleted": true, "key": "word:ability", "normalizedKey": "word:ability" }`

* エラー

  * 400: `{ "message": "Missing key parameter" }` / `{ "message": "Only word:* keys are allowed" }` / `{ "message": "Invalid key format" }`
  * 401: `{ "message": "Invalid token" }`
  * 500: `{ "message": "Failed to delete Upstash word key" }`

#### 4.3.4.2 セマンティック検索 `POST /api/search/semantic`

* 概要: 日本語・英語の意味ベースクエリ（例:「延期する」「感謝を伝えるメールで使う単語」）から、意味の近いTOEIC単語を返す。`/words` の「意味で探す」タブから呼ばれる

* 入口UI

  * `/words`: `WordsExplorerClient` の「意味で探す」タブ → `SemanticSearchPanel`（結果表示を含む唯一のUI）
  * TOP: `SemanticSearchLauncher`（ヘッダー直下・今日のおすすめの上）。結果UIは持たず、検索語を同一タブの `sessionStorage` へ保存してから `/words?mode=meaning&launch=<不透明ID>#word-explorer` へ遷移し、意味検索タブが `initialQuery` を自動実行する。検索語本文はURL、Vercelのリクエストログ、GA4の `page_location` に含めない。タブを閉じると一時データは削除され、URLだけを別タブへ共有しても検索語は復元されない
  * 検索語の一時保存・復元は `src/lib/semantic-launch-store.ts`（`sessionStorage`＋SPA遷移用メモリフォールバック）が担当する。URLパラメータ（`mode`/`launch`）の検証と組み立て、検索語の100文字切り詰めは `src/lib/semantic-launch.ts` の純粋関数に集約する
  * `WordsExplorerClient` は Next.js の `useSearchParams` でURLを購読し、ブラウザの戻る・進むや同一ページ内のモード変更へ追従する。静的プリレンダリングを保つため、`src/app/words/page.tsx` 側で同クライアントコンポーネントを `<Suspense>` に包む
  * `SemanticSearchPanel` は同一クエリの実行中Promiseをモジュール内Mapで共有する。React Strict Modeによるマウントeffect再実行でもAPIへの初回POSTは1回に抑え、各effect側のキャンセル判定でアンマウント後の状態更新を防ぐ
  * GA4: TOPカード送信時に `semantic_search_launch`（`query_length`・`source: top`）、検索実行時に `semantic_search`（`query_length`・`result_count`・`source: form|url`）。いずれも検索語本文は送信しない

* リクエスト

  * ヘッダー: `Content-Type: application/json`、`X-App-Source: toeic-client`（`/api/tts` と同じ同一オリジン検証あり）
  * ボディ: `{ "query": "延期する" }`（NFKC正規化・空白圧縮・小文字化後、最大100文字）

* 動作

  1. クエリを正規化し、RedisからVectorコーパス世代 `semsearch:index-version` を読む
  2. Redisのtop-K候補キャッシュ `semsearch:v3:<indexVersion>:<sha256先頭16桁>` を確認（ヒット時はレート制限を消費せず、現在の閾値を再適用して返却。TTL 7日）。世代取得に失敗した場合は、更新前の結果を誤って返さないよう結果キャッシュを読み書きしない
  3. キャッシュミス時は Upstash Ratelimit（sliding window、20回/分/IP、prefix `rl:semsearch`）を消費
  4. クエリを `gemini-embedding-001`（taskType: `RETRIEVAL_QUERY`、768次元、L2正規化）でembedding化
  5. Upstash Vector に `topK=10`・`includeMetadata: true` で近傍検索し、メタデータ（slug/term/level/japaneseTranslation）を検証
  6. 検証済みtop-K候補が1件以上の場合のみキャッシュへ保存し、`SEMANTIC_SEARCH_MIN_SCORE`（既定値 `0.82`）未満を除外して返却。閾値はキャッシュ読み出し時にも毎回適用するため、環境変数で変更しても旧フィルタ結果に固定されない

* レスポンス（200）

  * `{ "results": [{ "slug": "postpone", "term": "postpone", "level": "important", "japaneseTranslation": "延期する", "score": 0.91 }, ...], "cached": false }`（閾値以上、最大10件、関連度順）
  * UIではVectorスコアを確率・割合と誤認させないため「関連度○%」表示を行わない

* エラー

  * 400: `{ "error": "Invalid request body" }` / `{ "error": "Query is empty" }` / `{ "error": "Query too long" }`
  * 403: `{ "error": "Unauthorized source" }` / `{ "error": "Unauthorized origin" }`
  * 429: `{ "error": "Too Many Requests" }`（`Retry-After` ヘッダー付き）
  * 503: `{ "error": "Semantic search is not configured" }`（`UPSTASH_VECTOR_REST_URL/TOKEN` 未設定時）
  * 500: `{ "error": "Semantic search failed" }`

* ベクトルデータの投入・更新

  * 初回バックフィル: `npm run embed:words`（`scripts/embed-words.ts`）。全単語の WordDetails を Redis 優先で収集（未生成分は Gemini で生成して Redis に保存）→ `buildEmbeddingText` で1語=1ドキュメント化 → `gemini-embedding-001`（taskType: `RETRIEVAL_DOCUMENT`）でembedding → Upstash Vector に一括 upsert。単語リストはサイト本体と同じ `src/lib/word-source.ts` から読み込むため、既定はBlob（本番と同一コーパス）。Blobの全件投入が成功した場合だけ Vector インデックスを `range`で全件走査し、IDと `metadata.slug` が一致する単語ベクトルのうち、現行コーパスにないIDを `delete` する。`--limit=N` / `--only-cached` / `--source=local` / 生成失敗時は部分コーパスの誤削除を防ぐため削除同期をスキップする。upsertと必要な削除同期の後に `semsearch:index-version` を増分する。`--dry-run` / `--limit=N` / `--only-cached` / `--source=local|blob` オプションあり
  * 個別更新: `GET /api/revalidate/word?slug=<slug>&vector=true`（4.3.4参照）。upsert成功後に同じ世代キーを増分する
  * 世代更新前の結果キャッシュは削除スキャンせず、7日TTLで自然削除する

* 検索語の取り扱い

  * 検索語本文はクエリembedding生成のため Google Gemini API に送信される
  * TOPからの検索語は同一タブの `sessionStorage` に一時保存し、URLには不透明な起動IDだけを載せる。タブ終了時に削除される
  * Redisの結果キャッシュキーには検索語本文ではなくSHA-256由来の先頭16桁だけを使用する
  * GA4の `semantic_search` イベントには `query_length` と `result_count` だけを送信し、検索語本文は送信しない
  * UIと `/privacy` でGeminiへの送信を明示し、個人情報・機密情報を入力しないよう案内する

#### 4.3.5 サイトマップ生成 `GET /api/sitemap`

* 概要: サイト内の全ページ（静的ページ群および全単語詳細ページ）のURLを網羅した `sitemap.xml` を動的に生成する。
* 動作:
  * `next.config.ts` の `rewrites` 機能により、`/sitemap.xml` へのアクセスがこのAPIルートへルーティングされる。
  * 全単語一覧を `getAllWords()` で取得し、XML文字列を組み立てて返却する。
  * `Cache-Control` ヘッダーを用いてキャッシュされ、再生成の負荷を抑える。
  * **`noindex` ページ（`/favorites`・`/review`・`/login`・`*/listen`）は掲載しない**：sitemap に載せつつページ側で `noindex` を返すのは Google に矛盾したシグナルを送るため。
  * `lastmod` は静的ページ・ガイド記事（`article.updatedAt`）のみ出力する。**実更新日を管理していない URL（全単語詳細ページ、および日次ローテーションする `/today-words`）では `lastmod` を出力しない**：同一固定日を出すと Google が lastmod 自体を信用しなくなりクロール効率に悪影響が出るため、偽の日付を出すより省略する方針。`changefreq`/`priority` は残置しているが Google は無視する。

#### 4.3.6 サーバ側データ取得（`src/data/word-detail.ts` / `src/actions/word.ts`）

* 概要: 単語詳細（AI生成）を取得するためのサーバ関数群。ページ描画中（Server Component）に呼ばれる

* 関数

  * `getWordDetail(slug: string): Promise<WordDetails | null>`（`src/data/word-detail.ts`）: L1（Next.js Data Cache）でラップされた取得関数。Server Component から直接呼び出す
  * `fetchWordDetail(slug: string): Promise<WordDetails | null>`（`src/actions/word.ts`）: 上記を Server Action として公開（例外を握りつぶし `null` を返す）。学習モードのヒント取得などクライアントからの呼び出しに利用

* 返却

  * `null`: slugが単語リストに存在しない、または取得に失敗した場合

  * `WordDetails`: キャッシュまたは生成された詳細

* エラー

  * `GEMINI_API_KEY` 未設定時は例外を投げる（生成に失敗）

  * Upstash未設定/障害時も生成は継続するが、Redis読み書きは失敗する（ログに警告が出る）

## 5. 開発ガイドライン

### 5.1 コーディング規約

* TypeScriptの `strict`を前提に実装する（`tsconfig.json`）

* Next.js App Routerの構造に従い、UIは `src/app/**` 配下に配置する

* import alias `@/*` を使用する（`@` は `src` を指す）
